# 設計レビュー

`requirements.md` / `architecture.md` をレビュー。現状はどちらも概要レベルで、実装に着手するには不足している点がいくつかある。

## 懸念点・不足要件

- **データ永続化の形式が未定義**: 「ワークフローのステップ管理」を行うとあるが、ステップの状態（未着手/進行中/完了）や順序をどのファイル・形式で保持するか記載がない。`config/workflow.json` という名前だけがディレクトリ構成に出てくるが、中身のスキーマがない。
  → 実装難易度: 低。ただし後続のプロンプト生成・プレビュー機能がこのスキーマに依存するため、最初に固めるべき。

- **「プロンプト自動生成」の入力ソースが不明**: 何を元にプロンプトを組み立てるのか（ステップごとのテンプレート文字列か、`workspace/`内のファイル内容を埋め込むのか）が要件定義に書かれていない。
  → 実装難易度: 中。入力ファイルの読み込みタイミング（ステップ選択時か、都度リクエスト時か）次第でUIの応答性に影響する。

- **「成果物のリアルタイムプレビュー」の監視範囲が未定義**: `workspace/`配下全体を見るのか、特定ステップの`output_files`のみを見るのかで実装が変わる。ファイル削除・リネーム時の挙動も未記載。
  → 実装難易度: 中。ファイル監視（chokidar等）とWebSocket通知の設計が必要。

- **エラーハンドリングの記載がない**: `workflow.json`が壊れている場合、`workspace/`内の想定ファイルが存在しない場合の挙動が未定義。

- **複数AIの「担当AI」情報の管理方法が未定義**: ステップごとに文字列で持つのか、別途サービス一覧（名前・起動URL等）を管理するのか要件定義書からは読み取れない。

## 改善案

1. `config/workflow.json`のスキーマ（ステップの必須フィールド：id/index/ai_name/role/status/input_files/output_files/prompt_template）を要件定義書に明記する。
2. プレビュー対象を「選択中ステップの`output_files`」に限定するか「`workspace/`全体」にするかを決め、理由も添える。
3. ファイル不在・JSON不正時のフォールバック仕様（デフォルト値表示、エラーバナー等）を1行でも追記する。
4. AIサービス管理を要件定義に明示する（名前・URLの一覧を別ファイルで持つ想定であればその旨を記載）。

以上を踏まえ、実装フェーズでは①ワークフローデータモデルの確定 → ②ファイル監視基盤 → ③UI実装、の順で進めるのが妥当と判断する。
